# 面试卡的答案以要点为单位，并用要点数锚定自评

面试卡的答案不是一段散文，而是 3-6 条要点（`answer.key_points`），外加可选的展开叙述、代码片段与常见坑。自评的四档按钮按当前卡的要点总数动态标注命中区间（5 条要点时："重来 = 说到 0-1 条 / 困难 = 2-3 条 / 良好 = 4-5 条 / 简单 = 全中且能流畅串成话"）。

LeetCode 卡的自评有天然的客观锚点——代码写不出来就是不会。面试卡如果背面只有散文，翻开看到的是"哦这个我知道"，几乎必然点"良好"，自评虚高导致间隔虚长，SM-2 再准也无从挽救。要点提供可数的判定标准，把模糊的"我大概知道"变成"5 条里说到 2 条"。

不采用逐条勾选（checkbox 计算命中率）：每张卡多 3-6 次点击，与"快速过卡"的核心诉求正面冲突，而勾选一样可以自欺。失真的根因是"良好"这个词缺少判定标准，给它一个可数的定义就够了，无需增加交互成本。

由此派生出卡片粒度的硬规则：一张卡等于一次 1-2 分钟内可口述完的回答。"介绍一下你的项目"这类大题必须拆成"一分钟概述卡 + 若干深挖卡"，卡间用 `related_ids` 互链。因为 SM-2 的调度单位是一次可判定的回忆，一张覆盖 10 分钟叙述的卡只能得到模糊的平均自评，而拆开后真正遗忘的那一段会被单独高频重现。
