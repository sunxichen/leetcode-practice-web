# 面试问答题集（Interview Deck）

Status: ready-for-agent

领域词汇见 `CONTEXT.md`。相关决策记录：ADR-0001（一套算法按题集标定参数）、ADR-0002（每题集一份独立进度文档）、ADR-0003（要点作为答案单位并锚定自评）、ADR-0004（重要度取代难度并限制每日新卡）、ADR-0005（题集路由并列，共享会话外壳）。完整技术方案见 `docs/interview-deck-design.md`。

## Problem Statement

我在准备面试。除了算法题，我还要反复回忆三类内容：自己项目的深挖问答、技术路线的取舍理由、深度学习基础知识（其中一部分答案是代码，比如 attention 实现、loss 实现）。

现在这些内容散落在文档和笔记里，我只能靠"重读"来准备。重读的问题是它给我虚假的熟悉感：读过三遍的东西在面试现场依然说不出来，而我完全不知道哪些内容已经真的记住、哪些正在遗忘。我手上已经有一个跑得不错的间隔重复应用，但它只服务 LeetCode，题目结构、调度节奏、界面全是围绕"算法题"长出来的，我没法把面试内容塞进去。

我也没有时间在应用里手工录题——内容我会交给 LLM 批量生成，我只想尽快开始刷。

## Solution

在现有应用中增加第二个**题集**：面试问答题集。它与 LeetCode 题集在心智上完全独立——首页给两个入口，各自有各自的复习队列、各自的连续天数、各自的题库页。底层的记忆算法、进度存储机制、抽卡交互全部复用，只是标定值与内容形态不同。

面试**卡片**的正面是一个问题，背面以 3-6 条**要点**为主体，可带代码片段、展开叙述、常见坑与追问。**自评**的四档按钮按当前卡的要点数标注命中区间，把"我大概知道"变成"5 条里说到 2 条"这种可数判断。卡片粒度定死在"一次 1-2 分钟内可口述完的回答"，大题拆成概述卡加深挖卡并互链。

题目用**分类**（项目 / 技术路线 / 深度学习基础）与**重要度**（高频必答 / 常见 / 加分项）组织，不设难度。重要度决定有限的每日新卡额度先花在哪里。面试前可以用**全量扫题**模式无视到期时间集中冲刷，也可以在题库页**查阅**某张卡的答案而不触发自评。

内容以 JSON 文件进入仓库，由 LLM 依据 schema 生成，构建时校验；我不需要在页面里写任何东西。

## User Stories

### 开始复习

1. 作为复习者，我想在打开应用时看到两个题集入口并各自显示待复习数与新卡数，这样我第一眼就知道今天该刷哪边。
2. 作为复习者，我想点进面试题集后看到与 LeetCode 题集一致的模式选择界面，这样我不需要学习第二套交互。
3. 作为复习者，我想有一个"智能复习"入口自动安排今天该刷的面试卡，这样我不必自己决定复习什么。
4. 作为复习者，我想按分类开启一次会话（只刷项目题、只刷深度学习基础），这样我能针对某一轮面试集中准备。
5. 作为复习者，我想按重要度开启一次会话（只刷高频必答），这样时间不够时我能优先保住必答题。
6. 作为复习者，我想有"攻克最弱"入口挑出我最常忘的面试卡，这样我能集中处理薄弱点。
7. 作为复习者，我想在面试前一晚用全量扫题模式把某个分类的全部卡按重要度过一遍，即使它们今天并不到期。
8. 作为复习者，我想在没有任何卡到期时看到平静的空状态而不是被硬塞新卡，这样我知道今天可以收工。

### 刷卡过程

9. 作为复习者，我想在卡片正面只看到问题、分类、重要度和标签，这样我能先真正尝试回忆而不被答案干扰。
10. 作为复习者，我想在正面常驻看到这张卡有几条要点，这样我知道该答到多少，能自己判断有没有说完。
11. 作为复习者，我想在正面不看到任何调度信息（间隔天数、学习步数），这样我的自评不被"系统认为我应该记得"所诱导。
12. 作为复习者，我想在卡住时点一个按钮拿到一句方向提示（而不是答案），这样我有机会靠提示自己想起来。
13. 作为复习者，我想在没有写提示的卡上看不到提示按钮，这样界面不出现点了没反应的死控件。
14. 作为复习者，我想翻面后第一眼看到要点列表，这样我能逐条对照自己刚才说了什么。
15. 作为复习者，我想在带代码的卡上看到语法高亮的代码片段，并能一键复制，这样我能核对实现细节。
16. 作为复习者，我想在一张卡有多段代码时通过左右切换浏览（如朴素实现与带 mask 的版本），这样它们不必挤在一起。
17. 作为复习者，我想代码片段按自己声明的语言高亮（Python、伪码、YAML 等），而不是一律当成 Python。
18. 作为复习者，我想看到这张卡的常见坑与可能的追问，这样我准备的是一场对话而不是一段独白。
19. 作为复习者，我想把展开叙述折叠起来，这样复习时默认只看要点，需要补细节时再展开。
20. 作为复习者，我想从一张概述卡跳到它的深挖卡（以及反向跳回），这样被拆开的大题仍然是一个整体。
21. 作为复习者，我想四档自评按钮直接标出命中几条要点对应哪一档，这样"良好"有客观定义而不是凭感觉。
22. 作为复习者，我想自评区间按当前卡的要点总数自动换算，这样 3 条要点的卡和 6 条要点的卡各自成立。
23. 作为复习者，我想自评不需要逐条勾选，这样每张卡只花一次点击，刷卡速度不被拖慢。
24. 作为复习者，我想在误点自评后能撤销，这样一次手滑不会污染这张卡的调度。
25. 作为复习者，我想用键盘快捷键翻面与自评，这样在电脑上能高速过卡。

### 调度与节奏

26. 作为复习者，我想面试卡的学习步长按"1-2 分钟一张"标定而不是沿用算法题的节奏，这样重现时机落在我真的需要被再问一次的时刻。
27. 作为复习者，我想每天被引入的新面试卡有上限，这样不会在首日灌进几十张、次日同时到期形成雪崩。
28. 作为复习者，我想新卡按重要度顺序引入，这样有限的额度先花在会被问到的题上。
29. 作为复习者，我想答错的卡在同一次会话内再次出现，这样我当场就有一次重新回忆的机会。
30. 作为复习者，我想面试卡的复习间隔上限比算法题更紧，这样答案里的数字、公式、项目指标不会隔太久才被检验。
31. 作为复习者，我想会话结束时看到本次统计与该题集的连续天数，这样我知道自己刚才做了什么、坚持了多久。
32. 作为复习者，我想两个题集的连续天数各自统计，这样"今天只刷了面试题"不会让另一边的记录显得虚假。

### 题库与查阅

33. 作为复习者，我想在面试题库页搜索问题文本与标签，这样我能立刻找到某张卡。
34. 作为复习者，我想按分类与重要度筛选题库，这样我能看清某一类题的全貌。
35. 作为复习者，我想用语义筛选看"待复习 / 即将到期 / 易遗忘 / 未学"，这样我能评估自己的准备程度。
36. 作为复习者，我想在题库列表里就地展开某张卡的答案纯查阅，这样"我当时准备的答案是什么"不需要走一遍自评流程。
37. 作为复习者，我想查阅行为完全不写入调度状态，这样看着答案确认不会被记成一次成功的回忆。
38. 作为复习者，我想在题库里对某张卡单独点"去复习"进入单卡模式，这样我能定向重刷一张卡。
39. 作为复习者，我想在题库列表看到每张卡的熟练度与下次复习时间，这样我不必进入卡片就能判断状态。

### 内容生产

40. 作为题库作者，我想在仓库里有一份 schema 文档，包含字段定义、标准范例与可直接复制的生成 prompt，这样我把项目文档丢给 LLM 就能拿到合规的题目 JSON。
41. 作为题库作者，我想题库按分类分成多个文件，这样 LLM 一次只产出一个领域、diff 可读、我 review 得过来。
42. 作为题库作者，我想卡片 id 是带分类前缀的语义 slug，这样互链关系人眼可读、插入新题时不需要重排编号。
43. 作为题库作者，我想构建时自动校验题库（id 唯一、要点条数合规、互链指向存在的卡、语言合法），这样坏数据在构建阶段失败而不是在我刷卡时白屏。
44. 作为题库作者，我想校验脚本顺带生成首页需要的轻量摘要，这样我不会因为忘了额外一步而导致首页计数偏差。
45. 作为题库作者，我不想在应用页面里录入或编辑题目，内容一律以文件形式进仓库。

### 不退步

46. 作为现有 LeetCode 题集的使用者，我想我的复习进度在这次改动后一条不丢，这是不可协商的。
47. 作为现有使用者，我想 LeetCode 题集的调度结果在重构前后逐位一致，这样我已经建立的复习节奏不被静默改变。
48. 作为现有使用者，我想现有的 URL 和深链继续可用，这样我的书签和 PWA 图标不失效。
49. 作为现有使用者，我想在手机刷面试题、在电脑刷算法题时两边进度互不覆盖。
50. 作为现有使用者，我想应用继续能离线打开，这是它作为 PWA 的基本前提。

## Implementation Decisions

### 题集作为一等概念

引入题集配置这一概念：一个题集聚合了它的卡片数据源、调度参数、可选会话模式清单、卡片正反面渲染组件。两个题集共用同一套记忆算法与同一套进度存储机制，差异全部通过题集配置注入。未来增加第三个题集（如系统设计）只需新增一份配置。

### 内容模型

面试卡片的字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | 带分类前缀的语义 slug |
| question | 是 | 问题文本 |
| category | 是 | 项目 / 技术路线 / 深度学习基础，三选一 |
| tags | 是 | 细粒度主题，可多个 |
| priority | 是 | 高频必答 / 常见 / 加分项 |
| hint | 否 | 一句话方向指引，不泄露内容 |
| answer.key_points | 是 | 3-6 条原子要点 |
| answer.elaboration | 否 | 展开叙述、推导 |
| answer.code | 否 | 代码片段数组，每段含标签、语言、代码、可选说明 |
| answer.pitfalls | 否 | 常见坑与追问点 |
| follow_ups | 否 | 可能的追问 |
| related_ids | 否 | 互链，用于概述卡与深挖卡 |

**不设难度字段**（ADR-0004）。代码片段**不复用算法题的解法类型**——后者强制时间/空间复杂度与思路摘要三个必填字段，对 loss 实现是纯噪音；但轮播交互壳可以复用。代码语言走数据字段，不再硬编码 Python。

卡片粒度是硬规则而非建议：一张卡等于一次 1-2 分钟内可口述完的回答。大题拆成概述卡加深挖卡，通过互链组织。

### 调度

保留现有的 Anki 式状态机，不引入新算法，不上 FSRS（ADR-0001）。把原本散落在模块级常量里的调度参数收成一个显式传入的参数对象，涵盖学习步长、补习步长、毕业间隔、Easy 间隔、Hard 与 Easy 系数、间隔上限、失手恢复间隔、EF 相关阈值，以及队列编织所需的每分钟卡片数、learning 卡插回位置钳制上下界、每日新卡上限。

LeetCode 题集的参数取值与现有常量逐位相同。面试题集按 1.5 分钟一张标定：学习步长更短、插回窗口更窄、间隔上限更紧、每日新卡有上限。具体数值见技术方案文档的参数对照表。

**当前时间必须可注入**：目前状态机与队列生成内部直接读取系统时间，这既让行为不可测，也让"逐位一致"无法验证。改为由调用方传入。

智能队列的既有结构（learning 逾期最前 → 复习逾期与新卡按 3:1 编织 → learning 待到期按钳制位置插回）保持不变，两处按题集分支：新卡排序策略（面试题集按重要度，同级按 id）与每日新卡引入上限。每日统计需要新增"今日已引入新卡数"计数字段，现有的复习数、毕业数、失手数都不能替代它。

会话模式在面试题集下为：智能复习、按分类、按重要度、攻克最弱、全量扫题、单卡。全量扫题无视到期时间按重要度遍历（可限定分类），自评照常写入调度。

### 进度存储

每个题集一份独立的进度文档，键名按题集区分（ADR-0002）。进度读写接口接受题集标识并按白名单校验，键名不再硬编码。归并逻辑本身不变，按题集各跑一次。

每日统计与连续天数成为题集内的概念，不存在全局连续天数；会话总结文案标明所属题集。

进度 Context 从"单份进度"改为并行加载所有题集的进度，按题集标识取用，写入只写对应那一份。首页因此能同时显示两个入口的待复习数与新卡数。

### 界面与路由

面试题集使用与现有页面并列的新路由，现有 URL 一律不动（ADR-0005）。学习页那约 300 行的会话状态机（模式选择、队列推进、翻卡、自评、退出动画、会话统计、撤销）抽成与题集无关的会话 hook 加会话外壳组件，由题集配置注入差异，两条路由都是薄壳。这次重构必须保持现有学习页行为不变。

首页从"重定向到学习页"改为题集入口页。PWA 的起始地址本就是根路径，无需改动 manifest。底部导航保持"学习 / 题库"两个 tab（保护既有肌肉记忆），链接按当前所在题集解析；首页隐藏底部导航；头部品牌位显示当前题集名并可点击返回首页。

自评条的档位锚文案按当前卡要点数 n 换算：困难档下界为 0.4n 上取整，良好档下界为 0.8n 上取整，简单档要求全中且能流畅串成话。

题库页的筛选面板需要参数化筛选维度（难度 → 分类与重要度）。面试题库的列表项支持就地展开只读答案，此路径**不得写入任何调度状态**；另有独立入口进入单卡自评模式。查阅与复习是两种行为，不共用入口。

### 内容管线

题库按分类分文件，合并导出的接口与现有题目接口对齐。仓库内提供 schema 文档（字段定义、标准范例、可复制的生成 prompt）。校验逻辑做成纯函数，命令行脚本只是薄壳，校验内容包括 id 唯一性与 slug 规范、分类与重要度取值合法、要点条数在 3-6 且无空串、互链指向存在的卡、代码语言在高亮器支持范围内。同一脚本顺带生成首页所需的轻量摘要。

校验**直接串进构建脚本**，不使用 pre 脚本钩子——本仓库的包管理器默认不执行 pre/post 脚本。

### 数据加载

每个题集的完整 JSON 只被自己的路由静态引入，依赖框架的按路由代码分割使两份数据互不拖累。首页只读那份轻量摘要，避免同时引入两份完整题库。全部静态引入以保证 PWA 离线可用；按需 fetch 会引入加载态、缓存失效与离线三个新问题，本期不采用。

### 实施顺序

三个阶段，顺序不可调换：

1. **重构与抽象**，不加任何新功能：先写锁定现有行为的测试并手动备份一份进度快照，再做参数化、题集配置落地、进度 Context 改形、会话外壳抽取。
2. **面试题集最小可用**：类型、schema 文档、校验脚本、构建串联，**先只写 20-30 张真实卡并实际刷两天**验证要点粒度与卡片粒度规则，然后是卡片正反面、要点锚定的自评条、智能复习与全量扫题。
3. **外围补齐**：首页入口页、面试题库页（含只读展开查阅）、互链跳转、重要度徽章、按分类与按重要度模式、会话总结文案。

阶段二里"先写少量卡验证"是刻意的：若先生成几百张才发现要点粒度不对，全部要重做。

## Testing Decisions

好的测试只断言外部可观察的行为：给定输入产生什么输出、状态如何迁移。不断言内部实现（不测私有函数、不测调用次数、不快照 DOM 结构）。测试全部跑在 Node 环境，引入 vitest，不引入 jsdom 或组件测试基建。

本仓库**没有任何既有测试**，因此没有可参考的先例；这三个缝就是先例，后续测试应沿用它们的风格：纯函数、普通对象输入输出、显式注入当前时间。

### 缝一：会话引擎（最高价值）

一个模块边界，外部行为是"给定卡片集、进度、调度参数、会话模式、当前时间、一串自评 → 得出队列顺序与新的进度"。这一个缝覆盖了本次改动全部高风险逻辑。要测的行为：

- 状态机的 16 条迁移（4 个生命周期状态 × 4 档自评）各自产出的下一状态、下次到期时间、间隔与 EF
- 学习中的卡按 Again < Hard < Good 的顺序排列到期时间
- 失手后进入补习、成功补习后回到短间隔而非折半
- 间隔上限与 EF 下限的钳制生效
- **回归锚点**：用 LeetCode 题集的参数跑一组固定输入，断言结果与重构前逐位相同
- 智能队列的编织顺序：learning 逾期最前、复习逾期与新卡按 3:1 交织、learning 待到期插回位置落在钳制区间内
- 面试题集的新卡按重要度排序，同级按 id
- 每日新卡上限生效，且已引入计数跨天重置
- 全量扫题包含未到期的卡，按重要度排序，可按分类限定
- 攻克最弱的排序依据 EF 与失手次数

### 缝二：题库校验

纯函数：给定一组卡片，返回错误列表。要测的行为：id 重复、id 不符合 slug 规范、分类或重要度取值非法、要点为空或条数越界、互链指向不存在的卡、代码语言不被支持——每种坏数据都产出可定位的错误；合规题库返回空列表。同时断言摘要生成的输出与输入题库一致。

### 缝三：进度归并

纯函数加可注入的存储适配器。这是全项目最坏失败模式（丢进度）所在。要测的行为：本地较新时以本地为准并回写远端、远端较新时以远端为准、两侧皆空时产出初始结构、损坏的本地数据被安全丢弃而非抛错、旧字段结构被正确迁移到新结构且迁移是幂等的、**不同题集的读写互不干扰**。

### 明确不测

组件渲染与页面交互（翻卡动画、轮播、徽章、折叠）、样式、KV 与网络的真实往返、撤销的 UI 时序。这些靠手动验证：阶段一完成后在 LeetCode 题集上实刷一轮确认无回归。

## Out of Scope

- **FSRS 或任何新记忆算法**。需要完整复习历史来拟合参数，而当前只保存最后一次状态。若将来要上，第一步是先开始记录复习日志。
- **设定面试日期并倒推排期**的冲刺模式。引入新领域概念与一套一年只验证得了一两次的排期算法，收益不成比例。全量扫题模式覆盖绝大部分冲刺场景。
- **勾选式自评**（逐条勾选要点算命中率）。与"快速过卡"冲突，且勾选一样可以自欺。要点锚文案先跑两周再评估。
- **应用内题目编辑或导入界面**。内容一律以文件进仓库。
- **题库数据的按需加载**。会引入加载态、缓存失效与离线三个新问题，与 PWA 离线可用冲突。
- **全局连续天数**。两个题集心智独立，连续天数各自统计。
- **URL 迁移到统一的动态题集路由**。收益仅是好看，代价是现有深链与书签失效。
- **多用户与鉴权模型的改动**。仍是单用户加共享令牌。
- **复习日志（每次自评的历史记录）**。本期不做，但注意它是将来上 FSRS 的前提。
- **组件级与端到端测试**。

## Further Notes

- 自评虚高是本设计最大的未验证假设。要点锚文案是零交互成本的对冲手段，但它是否足够只能靠实刷检验。跑两周后观察失手次数的分布：若大量卡片反复失手，说明自评仍然偏松，届时再评估勾选式自评。
- 参数化重构最容易犯的错是"默认参数没对齐原常量"。这种 bug 不报错，只让复习间隔悄悄漂移，几周后才发现且无法追溯。这就是回归锚点测试必须先写的原因。
- 面试题集的调度参数是标定值而非定论，改动成本只是动题集配置里的常量。实刷两周后按体感调整是预期行为，不是设计失败。
- 现有代码中存在两处已知的遗留问题，本次不修但重构时不要放大：撤销操作不回滚会话统计中的档位计数（源码中已有注释承认此漂移）；进度数据里保留了若干标记为 deprecated 的旧字段镜像，供题库页读取。
- 题库摘要文件与题库本体存在同步义务，校验脚本需要能检出摘要过期，否则首页计数会静默偏差。
