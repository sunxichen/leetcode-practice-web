## 核心层（Opening Core）

### A1 · 请用一分半钟介绍一下这个项目：解决什么问题、怎么做的、你做了什么、结果如何。

我在做一个政务“边聊边办”场景的 AI 办事助手训练项目。比如老百姓提取公积金，不需要自己去填复杂的表单，而是跟 AI 助手对话，边聊边把事办了。这本质是一个**对话驱动的工作流决策问题**：模型需要主动追问缺失信息、按合规顺序调用业务接口、遇到异常时该转人工转人工、该拒办时拒办，办结后还要完整告知政策要求。

**技术方案上**，我首先将业务收敛在公积金的 4 个典型事项上；自研了一套领域无关的沙箱引擎和业务插件，通过主体感知机制在引擎层拦截越权调用，并能自动推导数据库终态；接着搭建了全合成数据管线与多层质量检验；然后基于 Qwen3-4B 模型，分别微调了办事模型和一个独立冻结的用户模拟器；在设计了基于数据库终态和语义告知的可程序化 Reward 之后，基于 GRPO 算法跑通了强化学习闭环。

这是我**独立负责的个人项目**，从架构设计、沙箱与数据流代码、SFT 与强化学习训练，到根因分析和评测，全部由我一人完成。

**结果方面**：SFT 基线在数据库终态、收尾动作、法定告知三项全对的严格标准下，达到了 80.1% 的成功率；在 500 步的 GRPO 强化学习训练中，模型在 96 条基准任务集上的成功率从 54.3% 提升到了 84.4%（净增 30.1 个百分点），在未见过的转人工测试集上提升了 9.2 个百分点且统计显著。目前，包含 1000 条未见题目的最终保留测试集已就绪，正在进行最终的双臂对照评测。

### A2 · 你能用一个具体的用户案例，把系统从开场到终局走一遍吗？

以“租房提取公积金”为例：

1. **开场与缺参追问**：用户开场说“我想从公积金里取点钱交房租”，没提身份证号和金额。模型识别出缺少必填要素，首先向用户追问身份证号与提取金额。
2. **时序合规调用**：用户补充了身份证号并说明提取两万元。此时模型不能直接调用提取接口，必须严格遵守业务前置依赖：先调用“实名核验”接口，通过后再调用“提取资格核验”接口。沙箱环境在底层强制校验这个调用时序，如果跳过核身直接提交，沙箱会直接拦截并返回错误码。
3. **业务提交**：两项核验均通过后，模型调用“租房提取申请”接口完成数据提交。
4. **合规告知与终局动作**：模型执行“办结（Finish）”动作，并在回复中准确告知老百姓业务已提交（口径是“已提交申请”而非“资金已到账”）、预计处理时效（如 3 个工作日）以及后续进度查询渠道。
5. **异常分支**：如果用户账户处于冻结状态，模型会识别并触发“转人工（Escalate）”；如果是冒用他人身份，模型会触发“明确拒绝（FinishWithRefusal）”。在整个交互中，扮演用户的模拟器遵循“不问不说”的信息释放规则，确保多轮交互的拟真度。

### A4 · 如果只能向面试官展示这个项目的一个点，你展示什么？

我最想展示的是：**在复杂智能体强化学习中，如何构建并审计一套真正可信的评测与度量体系**。这里面包含一个深刻的踩坑教训和一个正面的工程结果：

- **反面教训（伪失败的根因排查）**：强化学习初期，训练曲线一度近两个月毫无进展。我深入抽查单轮交互日志，发现瓶颈根本不是模型能力或算法失效，而是评测集中混入了大量“物理不可解”的任务。比如部分贷款查询任务要求“账户冻结时转人工”，但分配给模型的贷款接口根本查不到账户冻结状态，模型无论怎么探索都只能拿 0 分；还有部分冒用身份任务，冒用标记只写在文本备注里，核身接口压根未接入该逻辑。这些零分实际上在测试任务生成器的 Bug，而不是模型的能力。
- **正面结果**：定位根因后，我建立了严格的不变式校验门禁，清洗并重构了评测集，修复了评估链路。在这套可信的度量体系下，我们不仅在 96 题基准集上看到了 500 步训练带来 +30.1 个百分点的显著提升，还在未参与训练的泛化集上验证了转人工类任务 +9.2 个百分点的稳固提升。

这让我深刻认识到：在 Agent RL 落地中，确保环境与评测集的物理可解性与真实度，和算法调优同等重要。

### B1 · 政务“边聊边办”是什么场景？通用大模型直接做会怎么失败？

“边聊边办”是指群众在线上办事时，不再面对死板的几十项静态表单，而是通过多轮自然语言对话完成事项办理。它的本质是**对话驱动的工作流决策**——需要动态识别意图、追问补齐缺参、按合规时序调接口、处理异常分支，并在最后准确告知法定事项。

如果直接拿通用大模型（Prompt 方案）做这个场景，会遇到四类典型的工程失败模式：

1. **缺参时习惯性“脑补”**：用户没给身份证或账号，模型不追问反而自己编造参数去调接口；
2. **时序颠倒与越权**：不按政策规定的前置条件调用接口（例如没实名核验就直接查账户余额、甚至提交扣款）；
3. **遗漏法定告知要素**：办结后只说“办好了”，遗漏了政策要求的处理时效、凭证保管要求或下一步线下核验提示；
4. **缺乏合规拒办意识**：面对账户异常、限额超标或冒用身份等情况，缺乏明确的拒办与转人工边界，容易硬着头皮违规办理。

### B2 · 为什么从公积金单域、4 个 task_type 开始？你说的“强约束”具体指什么？

**选择公积金 4 个事项的原因**：

1. **方法论验证优先**：我的核心目标是验证一套可解释、可验证、可审计的政务 Agent 训练与评测方法论。先在一个高确定性领域跑通闭环，比摊大饼做泛化更有工程价值。
2. **事项同构且难度递进**：公积金业务从“账户查询（⭐）”到“租房提取（⭐⭐）”、“购房提取（⭐⭐⭐）”和“贷款还款查询（⭐⭐⭐⭐）”，难度从单只读接口跨越到多方合同校验、额度动态计算与复合分支，但底层都遵循“核身→验资→办理/分流→告知”的同构流程。

**“强约束”包含三个维度**：

1. **规则显式化**：每项业务都有标准政策卡（Policy Card），显式注入给模型，明确必填要素与分支红线；
2. **沙箱底层硬拦截**：沙箱引擎维护主体感知的调用状态（如“张三的实名核验不能用来查李四的账户”），非合规调用在底层直接阻断；
3. **终态程序化验证**：每个任务都有确定的目标数据库状态（Golden State），是否办成完全看数据落库事实，不依赖主观评分。

### B3 · 为什么不是规则 workflow、prompt engineering 或 rejection-sampling SFT，而要引入 RL？

1. **确定性逻辑交给规则，非确定性决策交给模型**：强规则（如接口时序、限额红线）由沙箱底层和业务网关硬性保证，不浪费模型参数去死记硬背；但“面对口语化输入何时追问、追问几个要素、在多分支下如何权衡终局动作、如何用自然语言准确告知”，这些策略无法穷举进固定状态机，需要模型具备多轮决策能力。
2. **可验证的终局让 RL 拥有确定性梯度**：政务场景办成没办成有确定的数据库状态和告知标准，不需要依靠脆弱的主观判分，这为强化学习提供了天然优质的 Reward 信号。
3. **关于拒绝采样微调（Rejection-Sampling SFT）的考量**：筛选成功轨迹做二次 SFT 是很强的基线。但我们在实验中发现，SFT 倾向于记住特定对话模板，面对用户长尾提问或模糊表达时，泛化和边界判别能力不足；而 GRPO 能通过组内对比，在多轮探索中拉开正确决策与错误决策的概率差距。

### C1 · 整个系统有哪些核心模块？它们怎么连成一个训练闭环？

系统主要由四个核心模块构成：

```
[ 任务实例 CanonicalTask ]
       │
       ▼
 ┌───────────┐     多轮对话      ┌─────────────────┐
 │ 办事模型   │ <──────────────> │ 冻结用户模拟器   │
 │ (Qwen-4B) │                  │ (Qwen-4B)       │
 └─────┬─────┘                  └─────────────────┘
       │ 工具调用
       ▼
 ┌───────────┐
 │ 沙箱引擎  │ ──> [ 真实数据库变更 + 执行日志 ]
 └───────────┘                │
                              ▼
                       ┌─────────────┐
                       │ Reward 评测  │ ──> [ GRPO 组内优势计算与策略更新 ]
                       └─────────────┘
```

1. **办事模型（Policy Agent）**：基于 Qwen3-4B + LoRA，负责理解用户意图、多轮追问、调用工具并给出最终结论；
2. **沙箱环境（Deterministic Sandbox）**：通用的轻量化仿真引擎，基于 SQLite 隔离数据，按任务注入初始状态，负责接口鉴权、时序校验与执行，并在结束后导出真实数据库快照；
3. **用户模拟器（User Simulator）**：独立微调并冻结的 4B 模型，根据用户画像和设定诉求与办事模型对话，遵循“不问不透露”的拟真交互原则；
4. **Reward 结算管线**：对话结束后统一评分——比对数据库实际终态与黄金终态、核对收尾动作，并结合语义模型（NLI+LLM）核查法定告知是否到位。

**闭环流程**：任务载入沙箱→办事模型与模拟器多轮交互→沙箱记录工具执行与数据库变更→Reward 管线结算得分→GRPO 计算组内相对优势并更新模型权重。

### C2 · 一次 RL rollout 是怎么跑的？Agent 能做哪些动作？

**Rollout 流程**：

1. 沙箱加载任务，系统将政策规则注入模型 Prompt；
2. 用户模拟器生成开场白，进入多轮对话交互；
3. 模型在每个交互回合内输出两段结构化内容：内部推理分析（`<analysis>`）和具体动作（`<action>`）；
4. 当模型输出收尾动作或达到最大轮次限制时，对话结束；
5. 沙箱导出最终数据库快照，Reward 模块计算综合得分。

**Agent 的 5 种动作空间**：

- `Ask_User`：向用户追问缺失要素；
- `Call_API`：调用沙箱业务接口；
- `Finish`：正常办结（合法终局）；
- `Escalate`：转人工审批（合法终局，如账户冻结或跨区域异常）；
- `FinishWithRefusal`：合规拒办（合法终局，如冒用身份或资质不符）。

评测时会按照 **4 类事项 × 3 种终局动作 = 12 个细分场景** 进行全方位矩阵式评估。

### C3 · 训练数据从哪来？全是合成的，怎么保证质量？

真实政务数据涉及公民隐私和业务保密，无法直接公开使用，因此数据全流程合成：

1. **参数空间采样**：任务工厂在预设的合法取值空间内，随机采样用户身份、公积金账户状态、提取金额等离散参数，组装成不可变的 `CanonicalTask` 任务定义；
2. **黄金终态生成**：沙箱根据任务参数自动执行标准接口序列，推导出基准数据库终态（`golden_final_state`），实现零人工标注；
3. **教师模型合成**：使用大模型教师（DeepSeek-V4）分别扮演 Agent 和用户，合成多轮对话轨迹；
4. **多层过滤漏斗（L0-L5）**：依次过滤格式错误、工具调用不合法、用户提前泄露参数、以及存在幻觉的样本；
5. **跨字段不变式门禁**：通过 21 项业务规则（如“贷款提取额度不得超过总额”、“非本人身份证必须触发冒用拦截”）进行硬性拦截，不合规任务直接丢弃。

**规模与数据发现**：SFT 阶段最终产出并使用了 3,840 条清洗后的合格对话。在数据分析中我发现，早期数据中“合规拒办”样本占比仅约 1.3%（54 条，其中身份冒用仅 30 条），样本极度稀疏，这也是早期模型在拒办场景下表现较弱的核心原因，为后续强化学习的针对性采样指明了方向。

### C4 · reward 是怎么设计的？怎么把“办成事、终局对、说到位、别违规、别低效”统一起来？

当前采用的是第 3 版 Reward 设计（Reward v3），在对话结束时统一计算：

```
综合得分 = 0.65 × 业务完成度(R_complete) + 0.35 × 法定告知(R_disclosure) - 0.10 × 轮数惩罚 - 0.10 × 失败调用惩罚
（若发生协议级硬违规，如调用不存在工具，总分直接置 0）
```

**核心设计亮点——终态动作门控（**`R_complete = R_state × R_terminal`**）**：

- `R_state`：数据库落库状态是否与 Golden 完全一致（0 或 1）；
- `R_terminal`：收尾动作是否完全正确（`Finish` / `Escalate` / `FinishWithRefusal`）；
- **解决的痛点**：在旧版设计中，完成度只看数据库是否对。在“应该转人工”的任务中，如果模型什么都没做就直接退出，数据库状态刚好未发生改变，模型也能拿到满分完成度，导致模型学不到转人工的边界。将两者相乘后，动作选错则完成度直接归零。

**数据源相互隔离**：完成度来自沙箱 SQLite 快照，法定告知来自 NLI 语义判别，效率扣分来自执行日志。单项无法通过投机取巧污染其他项。

### C5 · user simulator 为什么单独训练并冻结？验收结果如何？

**为什么必须冻结**：用户模拟器是强化学习训练环境的一部分，而不是被训练的策略。如果模拟器和办事模型同时在线更新，环境状态就会发生动态漂移，导致 Reward 信号失去可信基准，模型容易陷入互相迁就的虚假收敛。

**验收表现**：
模拟器在上线前设置了 5 道严格的准入门槛，实测全部达标通过：

1. **指令遵循率**：98.9%；
2. **信息释放时机正确率（不问不说）**：98.1%；
3. **人设与诉求一致性**：91.0%；
4. **异常早退率**：0.0%；
5. **对话跑题率**：0.0%。

残余约 1.9% 的偶发提前释放，主要集中在用户被连续追问时的多槽位合并回复，处于受控范围内。

### C6 · 为什么用 GRPO，而不是 PPO / DPO？

1. **算力与架构匹配**：我们使用的是双卡 RTX 4090 资源。PPO 需要维护与 Policy 模型同等大小的 Critic（价值网络），在多轮长文本对话下显存开销极大；GRPO 通过针对同一任务采样一组对话（K=8），利用组内样本的相对得分计算 Advantage，**彻底省去了 Critic 网络**，非常适合在有限算力下开展多轮 Agent 训练。
2. **损失函数与实现细节**：我们使用的底层框架在 Token 级别优化 CISPO 损失（裁剪重要性采样权重），在严格的 On-Policy 采样设置下，它的裁剪机制极少触发，实际表现高度贴近标准 GRPO。
3. **零方差组治理**：GRPO 的已知问题是全对（8/8）或全错（0/8）的组没有相对优势，无法提供有效梯度。为此我们在任务集中引入了可学性筛选机制，优先选择基线表现处于 2/8 到 6/8 难度区间的任务，保证每个 Batch 都有充沛的对比梯度信号。

### C7 · 怎么防止模型钻 reward 的空子（reward hacking）？

我们在架构和工程上做了多层防御：

1. **Reward 拆解与信息源隔离**：数据库状态、对话告知、执行效率由不同系统独立产出，单点投机无法拿高分；
2. **硬性违规一票否决**：违反核心协议或越权直接零分；
3. **告知判定双重校验**：采用本地自然语言推理模型（NLI）加大模型裁判（LLM Judge）双重语义判定，防止模型通过关键词复读骗取告知分。

**实际踩坑与自检机制**：
在早期一次实验中，模型在“正常办结”类任务上的得分突然大面积跌至 20% 左右。排查发现并非模型变笨，而是评测脚本的配置错误，将真实的裁判链替换成了一个默认返回 0 的 Mock 判定器。重新接入真实裁判链后，得分瞬间恢复至 77%。
这个教训促使我建立了一套**评测链路启动自检机制**：每次跑评测或 Rollout 前，系统必须先用固定探针用例跑通判定链路并自证通过，从工程上杜绝了虚假评估现象。

### D1 · SFT 阶段做到了什么水平？

在当前 Qwen3-4B 现役基线模型上，统一严格评测（要求数据库终态、收尾动作、法定告知全部正确）的结果如下：

- **整体严格成功率**：**80.1%**，严重硬性违规为 0.0%；
- **分业务事项看**：
  - 账户余额查询：100.0%（纯只读，已完全掌握）；
  - 租房提取：81.7%；
  - 购房提取：76.5%；
  - 贷款还款查询：61.3%（业务逻辑最复杂，分支较多）；
- **分收尾动作看**：
  - 转人工（Escalate）：93.5%；
  - 正常办结（Finish）：84.5%；
  - 明确拒办（FinishWithRefusal）：**20.0%**（显著短板）。

这一基线表明：SFT 模型在常规流程和转人工上表现较好，但在需要强证据才能触发的“明确拒办”场景下样本泛化较弱，这也成为后续强化学习重点攻坚的方向。

### D2 · RL 到底证明了什么、没证明什么？

**已经证明的成果**：

1. **定向缺陷突破**：在完全未参与训练的泛化测试集上，“转人工”类复杂任务成功率从 69.7% 提升至 79.0%（**净提升 9.2 个百分点**），置信区间严格不包含零，统计显著；
2. **训练收敛性良好**：训练集内部得分稳步上升（从 53.9% 提升至 61.7%）；
3. **基准集跨越式提升**：在完成 500 步 GRPO 训练（E1-E5）后，96 题中间基准集上的严格成功率从 SFT 基线的 54.3% 大幅提升至 **84.4%（净提升 30.1 个百分点）**。

**坦诚未完全证明/受限的部分**：

1. **全场景最终泛化结论仍在跑**：全场景 1000 题保留测试集的最终对比评测正在进行中，目前尚不能宣称全事项全收尾动作已全面超越；
2. **早期安全与效率的波动**：在未引入梯度守卫的初期实验中，曾出现过模型为追求流程简化而导致调用失败率微增的情况，证明 Reward 必须在效率和严谨性之间保持精细平衡。

### D3 · 项目里最严重的一次误判是什么？后来怎么证明原结论不成立？

最严重的一次误判是在项目中期，强化学习训练曲线一度连续近两个月几乎毫无长进，团队差点得出“4B 模型容量不足或 GRPO 在复杂多轮 Agent 上失效”的错误结论。

**排查与证伪过程**：
我没有盲目换大模型或改算法，而是沉下心对几百条失败轨迹做逐条代码级回溯。最终发现问题根本不在模型，而在于**任务生成器生成了大量逻辑矛盾的“死题”**：

1. **不可观测的任务**：在贷款查询任务中，要求“账户冻结即转人工”，但提供给 Agent 的贷款接口返回字段里根本没有“冻结状态”这一项，模型从物理上不可能做出正确判断；
2. **虚假身份冒用**：冒用标记仅写在任务描述文本里，底层的实名核验 Mock 接口根本没接入该逻辑，返回永远是“核验成功”。

**解决动作**：我为任务工厂编写了 21 项跨字段不变式（Invariants）校验程序，对历史生成的数千条任务进行清洗，直接退役了 247 条矛盾任务，并重新生成了结构自洽的数据集。在新数据集上重新训练后，RL 曲线立刻恢复了正常的正向学习态势。

### E1 · 模型和算力是什么配置？中途为什么把 policy 从 8B 换成 4B？

1. **性能瓶颈在多轮推理长尾**：实测发现训练瓶颈是多轮对话采样的串行耗时，导致训练 GPU 有超过 60% 的时间在等待 Rollout 结果；
2. **严谨的对照验证**：我没有盲目降级，而是用完全一致的数据集分别训练了 4B 和 8B 做严格对照。评测显示：4B 成功率 80.1%，8B 成功率 77.6%，硬性违规率均为 0.0%；
3. **吞吐提升显著**：在保持效果平手的前提下，4B 将端到端采样速度提升了约 1.5 倍，大幅降低了显存压力与训练迭代周期。

### E4 · 怎么证明看到的提升来自 RL 本身，而不是换了数据、judge 漂移或动作先验重排？

3. **因果归因的诚实边界**：该对照能够 100% 证明“训练后的模型显著优于 SFT 起点”；但如果要证明“该收益是否只能由 GRPO 带来，而非通过对成功样本做拒绝采样 SFT 带来”，还需要进一步跑二次微调的消融实验。在工程回答上，我们严格区分“模型能力的整体提升”与“算法特异性归因”。

### E6 · 怎么扩到第二个事项或第二个 domain？

- **框架层（100% 复用，无需修改）**：
  - 通用沙箱引擎（状态管理、主体鉴权、执行管线）；

- **业务插件层（只需新增一个声明式 Python Bundle）**：

  2. 注册业务 API 接口规范与 Mock 处理函数；
  3. 定义黄金执行链（`golden_chain`）以自动计算目标数据库状态；
  4. 声明目标数据库比对规则。

因此，扩展一个新业务（如“医保异地备案”）的边际成本仅在于定义业务规则本身，框架代码零改动。

## 延伸层（Opening Overflow）



### F1 · 什么是 golden_final_state？为什么不拿 golden 轨迹逐步比对？

`golden_final_state` 是任务初始化时，系统在沙箱内自动执行该业务的标准操作序列（Golden Chain）后，导出的**基准数据库最终快照**，完全由程序演算生成，零人工标注成本。

**为什么不做逐步轨迹比对**：
政务办事中存在大量合理的等价路径。例如用户同时缺姓名和身份证，模型先问姓名还是先问身份证、一次追问一个还是一起追问，都是合法的交互方式；只读查询接口的调用顺序也可以不同。如果做严格的每一步比对，就会扼杀模型的合理探索空间。因此我们采用**基于终局状态与收尾动作**的评测方式，而多余的轮次和失败调用则通过效率惩罚项自然约束。

---



### F2 · 怎么防止 Agent 违规操作，比如没验身份就动钱？

防范违规主要依靠**沙箱底层的结构性前置校验**，而不是寄希望于模型自觉：

1. **主体感知的前置拦截（Subject-Aware Precondition）**：沙箱内部维护了每个主体的核验状态账本。如果模型试图调用提取接口，底层会校验“该操作人是否已完成实名核验且资质合格”。如果是跨人操作或未核身操作，沙箱在底层直接拦截并返回错误码，根本不会发生数据库写入；
2. **错误分级与自愈机制**：被沙箱拦截的调用会被记为一次“失败调用（Failed Call）”并扣除少量效率分，但**不会立刻中断对话**。模型收到错误码后可以自主反思、补做核身，然后再继续办理并拿满完成度分；
3. **严重违规一票否决（Hard Violation）**：只有发生调用未授权工具、输出格式解析崩溃等底层协议错误时，才会直接判定 0 分并结束。

---



### F3 · 你的工作和 DeepSeek-R1 / DAPO 这些业界工作什么关系？

- **与 DeepSeek-R1 的关系**：我们在算法思想上借鉴了 DeepSeek-R1 所采用的 **GRPO 组内相对优势**机制，取消了 Critic 网络，将计算资源集中在多轮交互采样上；
- **与 DAPO 的关系**：我们借鉴了 DAPO 提出的“过滤零方差组、动态构建有效梯度样本”的思想，在任务集中设计了可学性筛选；
- **损失函数的实际落脚点**：在底层训练实现上，我们使用的是 MiniMax-M1 提出的 **CISPO 损失**（裁剪重要性采样权重），它通过保留 Token 级梯度贡献有效保障了训练稳定性；
- **差异与特色**：业界的 R1/DAPO 更多集中在单轮长思维链数学与代码推理上；而我们的工作探索了将组内相对优势应用于**多轮环境交互、带工具调用状态机以及确定性沙箱闭环**的智能体场景。

---



### F4 · RL 训练用的数据和 SFT 是同一批吗？

**早期版本存在部分同源，但在现役版本中实现了完全物理隔离**：

- 在早期实验中，部分测试任务与 SFT 数据同源，导致模型在部分长尾动作（如合规拒办）上缺乏新的探索空间；
- 在最新的 P5 版本中，我们全新生成了 3,100 条任务，并在任务生成阶段按“题目家族（Task Family）”做哈希隔离：训练集（1800 条）、验证集（300 条）和保留测试集（1000 条）之间彼此独立，开场白词汇与参数组合不重叠，确保强化学习和最终评测考察的是真正的泛化决策能力。

---



### F5 · 合成数据 + frozen simulator，会不会让模型只学会模板和 simulator 的怪癖？

这是基于模拟器做强化学习必须面对的理论风险。我们在设计上设置了三道防线：

1. **生成端多样性与隔离**：任务工厂在用户人设、开场白句式、口语化表达上做了组合参数采样，且测试集的 Prompt 模板与训练集严格隔离；
2. **退化策略监控**：在评测中增加了对模型“套路化复读”或“利用模拟器漏洞提前套话”等作弊模式的特征扫描；
3. **客观边界认知**：模拟器再拟真也无法完全等同于真实世界。这套训练系统的核心目标是让模型掌握严谨的“工作流决策骨架与合规时序”，上线前依然必须经过真实流量的影子模式校验。

---



### F6 · 项目里最重要的一次方向修正是什么？

最关键的一次方向修正是 **Reward 从 v1 纯数据库比对升级为 v3 的“终态动作门控机制”**。

- **旧设计的漏洞**：最初的 Reward 完成度只判断数据库是否与标准一致。这导致在“该转人工”或“该拒绝”的任务中，模型如果什么都不做直接退出，数据库恰好没有改动，居然能拿到 100% 的完成度满分。这导致模型失去了学习分流决策的梯度动力；
- **修正方案**：引入 `R_complete = R_state × R_terminal`。如果业务判定应该转人工，但模型错误地调用了办结动作，即便数据库没有被破坏，完成度得分也直接归零；
- **效果**：这一修正彻底拉开了不同收尾动作之间的分值差距，为后续强化学习在转人工和拒办场景上的能力突破奠定了基础。

---



### F7 · 选 RL 框架时最关键的几个约束是什么？ART 的实际代价是什么？

**选型时的三个决定性硬约束**：

1. **原生支持多轮 Agent 与 Tool-Calling 抽象**：框架必须能自然表达 Agent 与环境的多轮交互循环；
2. **自动化的 Token-Level Loss Masking**：在计算梯度时，系统必须自动屏蔽用户模拟器输入与工具返回内容的 Token，只对 Agent 自身输出的思考和动作计算损失；
3. **轻量与多卡分离部署**：能够很好地支持双卡 4090 架构（训练与推理分卡）。

**实际踩坑与工程代价**：
开源框架 ART 较新，在多卡环境下的分布式通信和 vLLM 兼容性上存在一些边缘 Bug，例如 LoRA 权重动态同步时的性能抖动。为了稳定运行，我们在外部编写了专门的进程守护、LoRA 权重定期合并（Merge-to-dense）以及显存清理逻辑，才保证了长程训练的稳定性。

### F8 · 思考链是怎么设计的？为什么不把 Think 做成独立动作？

模型在每个交互回合内，采用结构化标签顺序输出：先输出内部思考 `<analysis>`，紧接着输出具体动作 `<action>`。

**不把 Think 做成独立交互动作的原因**：

1. **优化目标更聚焦**：将思考做成独立动作，模型需要学习“当前要不要思考”；而内嵌思考让模型学习“在行动前如何结构化分析”。政务办事流程具有高度的规范性，每一次行动前都必须核对前置条件，因此内嵌思考更符合业务直觉；
2. **避免挤占对话轮次**：如果思考单独占一轮交互，会与对话轮数的惩罚项产生冲突，增加系统多余的调度开销。

### F9 · 训练中出现过哪些稳定性问题？怎么处理的？

主要解决过两类典型的训练稳定性问题：

1. **格式坍塌与梯度爆炸**：在早期的 On-Policy 训练中，模型在迭代到 30 步左右时偶尔会出现梯度范数（Grad Norm）异常尖峰，随后模型输出丢失 XML 格式标签。**解决方案**：引入了梯度守卫机制（当某批次梯度范数超过滑动中位数的 10 倍时直接跳过更新），并配合 Cosine 学习率平滑衰减，彻底解决了格式崩溃问题；
2. **异步流水线漂移（Async Stale Policy）**：曾尝试过异步 Rollout 管线以提升速度，但实测发现策略延迟（Off-Policy Lag）导致约 44% 的采样样本因策略漂移被丢弃，反而更慢。**解决方案**：果断收敛回严格的同步 On-Policy 训练模式，优先保证训练收敛的确定性。
